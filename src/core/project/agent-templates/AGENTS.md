# AGENTS.md

This project was generated by **SwallowKit**.

SwallowKit is part of this project's architecture and development workflow.
Treat it as a standing constraint during discovery, requirements clarification,
specification, planning, ticket decomposition, implementation, verification,
and review — not only during code generation.

## How SwallowKit Fits Into the Development Process

SwallowKit does **not** own the overall software development process.

If the user or another Agent Skill or framework defines a process for
requirements discovery, specification, planning, ticketing, TDD,
implementation, or review, continue to follow that process.

Use SwallowKit as the authoritative project-specific layer for:

- inspecting the current project
- understanding entities, routes, infrastructure, and responsibility boundaries
- determining which artifacts may be edited directly
- performing deterministic generation through plan/apply
- detecting drift
- verifying the resulting project
- enforcing human approval gates for sensitive operations

External development-process skills and SwallowKit are intended to compose.

A process skill decides **how to proceed**.
SwallowKit determines **how this SwallowKit project can be changed safely and reproducibly**.

## Specification and Planning Guidance

When producing or refining a specification:

- describe user-visible behavior and domain intent
- define acceptance criteria and important test seams
- treat SwallowKit's architecture and responsibility boundaries as
  implementation constraints
- avoid prematurely describing generated artifacts as manually implemented
  components
- do not duplicate work that SwallowKit can deterministically derive from its
  source of truth

For example, if adding a model field causes SwallowKit to regenerate backend,
BFF, UI, and infrastructure artifacts, the specification should primarily
describe the desired end-to-end behavior and the SwallowKit constraint.

It should not imply that every generated layer is an independent manual
implementation decision.

If whether SwallowKit supports the desired behavior affects the specification,
inspect the current capabilities before finalizing the spec.

## Ticket Decomposition Guidance

Prefer independently verifiable **vertical slices** of user or system behavior.

Do not split work into horizontal tickets such as:

- schema ticket
- backend ticket
- BFF ticket
- UI ticket
- infrastructure ticket

merely because those artifacts exist in separate layers.

When SwallowKit deterministically produces those layers, keep them inside the
same vertical slice whenever they represent one end-to-end behavior.

Example:

```text
Add priority support to Todo
  ├─ update the source-of-truth model
  ├─ use SwallowKit plan/apply to realign managed artifacts
  ├─ add any required ai-authored business logic
  ├─ add/update tests
  └─ verify the project
```

Ticket boundaries should reflect independently valuable and verifiable
behavior, not SwallowKit's generated file structure.

## Deterministic Changes: Plan → Apply → Verify

For autonomous or agent-driven generation, prefer the SwallowKit two-phase
workflow.

```text
inspect
   ↓
plan
   ↓
evaluate conflicts / approval requirements
   ↓
apply
   ↓
verify
```

Example:

```bash
{{runCmd}} swallowkit machine plan scaffold <model>
{{runCmd}} swallowkit machine apply scaffold --plan <planId>
{{runCmd}} swallowkit machine verify project
```

Do not bypass plan/apply by manually editing deterministic artifacts.

If a plan reports conflicts, determine whether existing hand-written behavior
must be moved to an ai-authored location or whether overwrite approval is
required.

Never invent or implicitly grant human approval.

## Authentication

Authentication is a **plan/apply operation**, not a free-form config edit.
Ownership of `swallowkit.config` is split:

- `auth.schemes` — owned by SwallowKit. **Always start with
  `{{runCmd}} swallowkit machine plan auth --provider <p> [--scheme <name>]`.
  Never hand-write `auth.schemes` entries**; apply auth appends them, and a
  hand-written scheme makes the plan fail with "already exists".
- `auth.authorization.policies` and `swa.allowedProviders` — hand-edited
  **after** apply (the config is an extension point; this edit is expected).
  `swa.allowedProviders` can also be set at plan time with
  `--allowed-providers github,aad`.

After `apply auth`, follow the returned `nextActions`:

1. Define `auth.authorization.policies` referencing the new scheme.
2. For `swa`: confirm `swa.allowedProviders`; generated login URLs use it.
3. For `external-token`: implement the generated verifier stub. It fails
   closed, and **verify passes with the stub in place** — a green verify does
   not mean external-token auth works end-to-end (`verify project` surfaces a
   `auth-verifier-stub` warning while the stub is unmodified).
4. Re-run plan/apply scaffold for models that need auth guards, then verify.

Use the `swallowkit-add-auth` Agent Skill or the
`.swallowkit/workflows/add-auth.md` runbook when available.

### Generated CRUD scope

Generated CRUD endpoints enforce the model's `authPolicy`
(authentication + roles) — **they do NOT scope data to the authenticated
user**. Any caller passing the policy can read or write any document. For
multi-user data where users may only touch their own records, add ai-authored
custom endpoints that derive the scoping key (e.g. `learnerId`) from the
verified principal — never from the request body — and restrict the generated
write endpoints to admin roles.

## Verification Is a Completion Gate

Before treating an agent-driven implementation as complete, run SwallowKit
verification:

```bash
{{runCmd}} swallowkit machine verify project
```

or the equivalent MCP operation.

Verification covers SwallowKit structural correctness, drift, type correctness,
and configured project checks.

When verification fails, use the structured failure explanation:

```bash
{{runCmd}} swallowkit machine explain failure
```

or its MCP equivalent, then repair the appropriate source and verify again.

Use the `swallowkit-verify-repair` Agent Skill or runbook when applicable.

SwallowKit verification answers:

> Is the SwallowKit project mechanically and structurally valid?

A semantic code review answers different questions:

> Is this implementation well designed?
> Does it satisfy the specification and user intent?

Therefore, perform SwallowKit verification before treating semantic code review
as the final quality gate.

## Human Approval Gates

A machine operation may return terminal states such as:

- `complete`
- `in-progress`
- `blocked`
- `requires-human`
- `failed`

Follow `nextActions`.

When the status is `requires-human`, stop and request the required human
decision.

Do not reinterpret `requires-human` as an error to work around.

Azure provisioning is a human-approved operation.

Use the `swallowkit-provision` Agent Skill or runbook and never bypass its
approval gate. A broad request to deploy does not itself grant the explicit
approval required by that workflow.

## Architecture

This is a full-stack application deployed on Azure with a TypeScript
frontend/BFF and an Azure Functions backend in {{backendLanguageLabel}}.

```text
Frontend (React / Next.js App Router)
  ↓
BFF (Next.js API Routes)
  ↓
Azure Functions
  ↓
Azure Cosmos DB
```

### Core architecture rules

1. Next.js API routes are a BFF/proxy layer. Do not place application business
   logic or direct database access there.
2. Zod schemas under `shared/models/` are the application model source of truth.
3. Do not duplicate model definitions across layers.
4. Azure Functions own backend business logic and data access.
5. SwallowKit-generated artifacts must be changed through their source of truth
   and deterministic generation workflow, not by hand.
6. Infrastructure is managed as code with Bicep. Respect SwallowKit ownership
   markers and boundaries.
7. Production access to Azure resources must follow the generated security
   architecture; do not introduce hard-coded credentials or connection strings.

### Backend-specific rules

{{backendRules}}

The backend owns `id`, `createdAt`, and `updatedAt`; never trust client-sent
values for these fields.

## Naming and Model Conventions

- Model schema files use `shared/models/{kebab-case}.ts`.
- The Zod schema constant and inferred TypeScript type use the same PascalCase
  name: `export const Todo = z.object(...); export type Todo = z.infer<typeof Todo>`.
- Re-export models from `shared/index.ts`.
- `id` is a required `z.string()`; only `createdAt` / `updatedAt` are optional
  backend-managed fields.
- Models may declare `partitionKey`, `authPolicy`, `displayName`, and
  `connectorConfig` as exported constants. Exact formats:
  `{{runCmd}} swallowkit machine inspect capabilities` (modelDeclarations).
- Cosmos DB containers use PascalCase plural names and default to `/id` as the
  partition key unless the model declares another key, e.g.
  `export const partitionKey = '/learnerId';` (the field must exist in the
  schema).

## Final Rules

Do not:
