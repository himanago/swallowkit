# AGENTS.md

This project was generated by **SwallowKit**.

SwallowKit is part of this project's architecture and development workflow.
Treat it as a standing constraint during discovery, requirements clarification,
specification, planning, ticket decomposition, implementation, verification,
and review — not only during code generation.

## How SwallowKit Fits Into the Development Process

SwallowKit does **not** own the overall software development process.

If the user or another Agent Skill or framework defines a process for
requirements discovery, specification, planning, ticketing, TDD,
implementation, or review, continue to follow that process.

Use SwallowKit as the authoritative project-specific layer for:

- inspecting the current project
- understanding entities, routes, infrastructure, and responsibility boundaries
- determining which artifacts may be edited directly
- performing deterministic generation through plan/apply
- detecting drift
- verifying the resulting project
- enforcing human approval gates for sensitive operations

External development-process skills and SwallowKit are intended to compose.

A process skill decides **how to proceed**.
SwallowKit determines **how this SwallowKit project can be changed safely and reproducibly**.

## Specification and Planning Guidance

When producing or refining a specification:

- describe user-visible behavior and domain intent
- define acceptance criteria and important test seams
- treat SwallowKit's architecture and responsibility boundaries as
  implementation constraints
- avoid prematurely describing generated artifacts as manually implemented
  components
- do not duplicate work that SwallowKit can deterministically derive from its
  source of truth

For example, if adding a model field causes SwallowKit to regenerate backend,
BFF, UI, and infrastructure artifacts, the specification should primarily
describe the desired end-to-end behavior and the SwallowKit constraint.

It should not imply that every generated layer is an independent manual
implementation decision.

If whether SwallowKit supports the desired behavior affects the specification,
inspect the current capabilities before finalizing the spec.

## Ticket Decomposition Guidance

Prefer independently verifiable **vertical slices** of user or system behavior.

Do not split work into horizontal tickets such as:

- schema ticket
- backend ticket
- BFF ticket
- UI ticket
- infrastructure ticket

merely because those artifacts exist in separate layers.

When SwallowKit deterministically produces those layers, keep them inside the
same vertical slice whenever they represent one end-to-end behavior.

Example:

```text
Add priority support to Todo
  ├─ update the source-of-truth model
  ├─ use SwallowKit plan/apply to realign managed artifacts
  ├─ add any required ai-authored business logic
  ├─ add/update tests
  └─ verify the project
```

Ticket boundaries should reflect independently valuable and verifiable
behavior, not SwallowKit's generated file structure.

Use the `swallowkit-modify-model` Agent Skill when available.

Otherwise read and follow the equivalent runbook under
`.swallowkit/workflows/`.

Never repair schema drift by directly patching SwallowKit-managed artifacts.

Additional model-change facts:

- The shared package is consumed through its built `dist/`. `verify project`
  rebuilds it automatically before typecheck; when typechecking manually,
  build the shared package first (stale `dist/` shows up as
  "no exported member" errors).
- Seed JSON under `dev-seeds/<environment>/<model-kebab-case>.json` is only applied by
  `{{runCmd}} swallowkit dev --seed-env <environment>`; editing the files
  alone does nothing.
- Seed files use the singular kebab-case model filename, not the plural Cosmos
  container name; for example, `learning-profile.json` maps to
  `shared/models/learning-profile.ts` and contains a top-level JSON array of
  documents with valid non-empty `id` values. `--seed-env` replaces data in
  each matching local Emulator container before startup; without it, existing
  data is preserved. Do not inject demo data through HTTP handlers, startup
  hooks, or empty-database fallbacks, or replace this workflow with custom
  flags, reset APIs/UIs, or backend importers. Offline fixture tools may write
  only standard seed files and must not run from the backend. Keep legitimate
  business initialization separate from demo data.
- Confirm startup output identifies the expected seed file/container and
  applied document count. Missing environments, unmatched files, or zero
  applied targets are not successful seed application.

## New Models / CRUD Features

For every new persistent model, follow the current SwallowKit model-creation
and infrastructure-generation workflow, **whether or not it uses custom APIs**.
Adding a hand-written schema alone is not completion.

1. Inspect current capabilities and entities. Use
   `{{runCmd}} swallowkit create-model <name>` or the agent-facing equivalent
   `{{runCmd}} swallowkit machine generate model <name> --overwrite never`.
   This creates the schema, shared export, model metadata, and versioned
   Bicep migrations under `infra/migrations/`, recorded in its `manifest.json`.
   New Cosmos models become provision targets without requiring CRUD scaffold.
   Preview every write with `--dry-run`, or use `machine plan model <name>`
   and `machine apply model --plan <planId>`.
2. Author domain fields. For an existing hand-written model, run
   `{{runCmd}} swallowkit migrations add-model <model>` to register infrastructure
   without rewriting the schema or generating CRUD. Scaffold is optional for
   custom APIs. If the partition key changes after template creation, use
   `migrations add-model <model> --refresh-pending --resource-group <rg>`
   (optionally `--subscription <id>`): this performs read-only Azure checks.
   Only an unmodified generated migration proven pending for that target may
   be refreshed. Unknown state and applied partition-key changes are blocked.
   The subscription is resolved once and pinned in plans and queries. Empty
   or missing expected deployment history blocks refresh. Retained history
   cannot reveal deleted attempts or out-of-band changes: do not refresh if
   history was removed/truncated or the artifact was applied elsewhere.
   Existing baseline-owned containers remain wired in `infra/main.bicep`;
   do not add duplicate containers or edit applied migrations.
3. Verify the correspondence between the model, container name/partition key,
   Bicep wiring or migration manifest, and `.swallowkit/artifacts.json`
   generation ledger. Use `machine inspect entities`, `machine inspect infra`,
   `machine inspect drift`, and `machine verify project`; inspect the actual
   files too. Local generation/verification does not mean Azure was deployed.
   Missing or stale container definitions and schema-analysis failures block
   verification/provisioning; never treat omitted models as a passing result.

The parser prefers the filename-matching PascalCase schema export, then the
legacy camelCase `Schema` export; multiple unmatched candidates stop with a
structured error. Helper ordering must not change the selected entity.
Separate id-less helpers are excluded only with actual embedded references
reachable from persistent models and no persistence metadata. Unsupported helper
fields still block; helper dependencies remain fingerprinted. Unreferenced
id-less files and invalid persistence ids block with classification diagnostics.
`z.record` is currently unsupported by the generation contract (including
string values); failures identify file/schema/field/reason. Do not reorder
schemas, edit the ledger, or cast away dictionary value types as a workaround.

Custom APIs and non-persistent types remain ai-authored. Connector-backed
models follow their connector workflow rather than inventing Cosmos containers.
If generation is omitted, state the reason and unfinished work explicitly.
Never describe a project as deployable while required persistence infrastructure
is missing; do not hand-edit managed infrastructure or the generation ledger.

Use the `swallowkit-add-model` Agent Skill when available.

Otherwise follow the equivalent runbook under `.swallowkit/workflows/`.

The agent may author domain-specific schema fields and custom behavior, but
SwallowKit should generate framework-owned CRUD artifacts.

Do not manually recreate boilerplate that SwallowKit owns.

## Authentication

Authentication is a **plan/apply operation**, not a free-form config edit.
Ownership of `swallowkit.config` is split:

- `auth.schemes` — owned by SwallowKit. **Always start with
  `{{runCmd}} swallowkit machine plan auth --provider <p> [--scheme <name>]`.
  Never hand-write `auth.schemes` entries**; apply auth appends them, and a
  hand-written scheme makes the plan fail with "already exists".
- `auth.authorization.policies` and `swa.allowedProviders` — hand-edited
  **after** apply (the config is an extension point; this edit is expected).
  `swa.allowedProviders` can also be set at plan time with
  `--allowed-providers github,aad`.

After `apply auth`, follow the returned `nextActions`:

1. Define `auth.authorization.policies` referencing the new scheme.
2. For `swa`: confirm `swa.allowedProviders`; generated login URLs use it.
3. For `external-token`: implement the generated verifier stub. It fails
   closed, and **verify passes with the stub in place** — a green verify does
   not mean external-token auth works end-to-end (`verify project` surfaces a
   `auth-verifier-stub` warning while the stub is unmodified).
4. Re-run plan/apply scaffold for models that need auth guards, then verify.

Use the `swallowkit-add-auth` Agent Skill or the
`.swallowkit/workflows/add-auth.md` runbook when available.

### Generated CRUD scope

Generated CRUD endpoints enforce the model's `authPolicy`
(authentication + roles) — **they do NOT scope data to the authenticated
user**. Any caller passing the policy can read or write any document. For
multi-user data where users may only touch their own records, add ai-authored
custom endpoints that derive the scoping key (e.g. `learnerId`) from the
verified principal — never from the request body — and restrict the generated
write endpoints to admin roles.

## Verification Is a Completion Gate

Before treating an agent-driven implementation as complete, run SwallowKit
verification:

```bash
{{runCmd}} swallowkit machine verify project
```

or the equivalent MCP operation.

Verification covers SwallowKit structural correctness, drift, type correctness,
and configured project checks.

When verification fails, use the structured failure explanation:

```bash
{{runCmd}} swallowkit machine explain failure
```

or its MCP equivalent, then repair the appropriate source and verify again.

Use the `swallowkit-verify-repair` Agent Skill or runbook when applicable.

SwallowKit verification answers:

> Is the SwallowKit project mechanically and structurally valid?

A semantic code review answers different questions:

> Is this implementation well designed?
> Does it satisfy the specification and user intent?

Build, typecheck, unit tests, fixture checks, readiness checks, and
`machine verify project` are mechanical evidence, not proof of working
application persistence or a user flow. For startup, persistence, API, or UI
changes, use normal `{{runCmd}} swallowkit dev` and exercise the real app
through the same-origin Next.js BFF, standalone Azure Functions runtime, and
configured database. Verify writes by reloading the relevant UI/API result and
restarting without re-seeding; check invalid input, missing IDs, and
authentication when relevant. Report evidence and limits separately (local
Emulator or Azure Cosmos DB, mock or real AI, fixed development identity or
real authentication). HTTP success or host readiness does not clear
`AzureWebJobsStorage` or other startup warnings. Missing prerequisites remain
blocked/unverified; unrelated green tests do not fill the gap. Documentation-only
changes do not require database startup.

Therefore, perform SwallowKit verification before treating semantic code review
as the final quality gate.

## Human Approval Gates

A machine operation may return terminal states such as:

- `complete`
- `in-progress`
- `blocked`
- `requires-human`
- `failed`

Follow `nextActions`.

When the status is `requires-human`, stop and request the required human
decision.

Do not reinterpret `requires-human` as an error to work around.

Before connecting to or changing local data, inspect existing Emulator
services, endpoint, and ports; do not restart a service already in use. Before
seed replacement or container recreation, confirm the actual endpoint,
effective database and container targets, isolated dev/test database and
ports, and worktree isolation from configuration and startup output. Treat
existing, shared, or production data as protected and follow explicit approval
rules before destructive operations. Do not disable TLS, bypass certificate
validation, or change global machine settings to work around connection
problems. Stop only processes started for this task, never unrelated services
by process name, and disclose local untracked configuration or database
leftovers.

Azure provisioning is a human-approved operation.

Use the `swallowkit-provision` Agent Skill or runbook and never bypass its
approval gate. A broad request to deploy does not itself grant the explicit
approval required by that workflow.

## Architecture

This is a full-stack application deployed on Azure with a TypeScript
frontend/BFF and an Azure Functions backend in {{backendLanguageLabel}}.

```text
Frontend (React / Next.js App Router)
  ↓
BFF (Next.js API Routes)
  ↓
Azure Functions
  ↓
Azure Cosmos DB
```

### Core architecture rules

1. Next.js API routes are a BFF/proxy layer. Do not place application business
   logic or direct database access there.
2. Zod schemas under `shared/models/` are the application model source of truth.
3. Do not duplicate model definitions across layers.
4. Azure Functions own backend business logic and data access.
5. SwallowKit-generated artifacts must be changed through their source of truth
   and deterministic generation workflow, not by hand.
6. Infrastructure is managed as code with Bicep. Respect SwallowKit ownership
   markers and boundaries.
7. Production access to Azure resources must follow the generated security
   architecture; do not introduce hard-coded credentials or connection strings.
8. Production persistent application data uses the configured Azure Cosmos DB
   infrastructure. Local development uses the Cosmos DB Emulator through the
   standard `{{runCmd}} swallowkit dev` workflow.
9. Custom APIs and business logic use the project's standard Cosmos connection
   and effective database name, including linked-worktree isolation shown in
   configuration and startup output. Do not add a separate database, storage
   path, or production-only startup flag without an explicit requirement.
10. If Cosmos DB, credentials, or a required container are unavailable, report
    the operation as blocked or unverified and follow the standard
    infrastructure workflow. Never mask the problem with file, JSON, SQLite,
    or in-memory application storage or a fallback. Unit-test doubles are
    allowed but are not database or runtime evidence.
11. Do not assume alternate persistence is unsupported or introduce it by
    default. For an explicitly requested alternative or configured external
    connector, inspect current capabilities and responsibility boundaries first.

### Backend-specific rules

{{backendRules}}

The backend owns `id`, `createdAt`, and `updatedAt`; never trust client-sent
values for these fields.

## Naming and Model Conventions

- Model schema files use `shared/models/{kebab-case}.ts`.
- The Zod schema constant and inferred TypeScript type use the same PascalCase
  name: `export const Todo = z.object(...); export type Todo = z.infer<typeof Todo>`.
- Re-export models from `shared/index.ts`.
- `id` is a required `z.string()`; only `createdAt` / `updatedAt` are optional
  backend-managed fields.
- Models may declare `partitionKey`, `authPolicy`, `displayName`, and
  `connectorConfig` as exported constants. Exact formats:
  `{{runCmd}} swallowkit machine inspect capabilities` (modelDeclarations).
- Cosmos DB containers use PascalCase plural names and default to `/id` as the
  partition key unless the model declares another key, e.g.
  `export const partitionKey = '/learnerId';` (the field must exist in the
  schema).
